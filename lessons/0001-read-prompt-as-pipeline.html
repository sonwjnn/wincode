Đọc một system prompt như một pipeline

Tangible win: sau bài này, bạn có thể nhìn vào source và chỉ ra đâu là base tĩnh, đâu là context động, đâu là tool contract — thay vì gọi tất cả là “prompt”.

1. Đổi câu hỏi

Đừng hỏi: “File system prompt nằm ở đâu?” Hãy hỏi: “Request cuối cùng được lắp từ những block nào, theo thứ tự nào?”

Mô hình làm việc: request = instruction base + runtime context + tool contract + user turn

Đây là mô hình khái niệm, không phải mọi hệ thống đều nối bốn phần thành một string. Tool contract thường đi qua API riêng; compaction cũng có assembly path riêng.

Ba ranh giới cần giữ

  1. Base: policy và role tương đối ổn định.
  2. Context: cwd, rules, skills, git state hoặc instructions thay đổi theo workspace/request.
  3. Tools: tên, mô tả và input schema để model gọi đúng; không nhất thiết phải lặp lại trong prose.

2. Ba implementation, ba composition seam

Pi: một string, nhiều đoạn ghép

buildSystemPrompt() bắt đầu bằng default hoặc custom prose, rồi thêm tool snippets/guidelines, append text, project context, skills và cwd. Custom prompt thay thế phần prose mặc định nhưng vẫn nhận phần tail động đó. Đọc source Pi.

Câu hỏi khi đọc source: “Đoạn nào là default branch? Đoạn nào có gate theo tool/resource?”

Oh My Pi: template + ordered blocks

OMP giữ phần instruction tĩnh trong Markdown/Handlebars templates. Builder chuẩn bị dữ liệu động rồi trả về các block theo thứ tự: instruction, computer-safety tùy chọn, project/environment footer và active-repository block. Đọc builder OMP.

Câu hỏi khi đọc source: “Block nào có thể cache ổn định? Block nào thay đổi theo workspace?”

OpenCode: provider base + request preparation

OpenCode chọn static .txt theo provider/model, hoặc dùng agent prompt. Sau đó request layer thêm environment, discovered instructions, MCP instructions, skills và structured-output directive. Tool descriptions/schema đi qua AI SDK tools riêng. Đọc request preparation và đọc tool resolver.

Câu hỏi khi đọc source: “Phần nào provider-specific? Phần nào là runtime service chung?”

Wincode hiện tại: composition root đang nhỏ hơn: base instructions + resolved agent instructions; tools truyền riêng và skill activation là user skill-context message. Đây là điểm xuất phát để so sánh, không phải kết luận rằng Wincode phải copy OMP. Xem evidence matrix đầy đủ.

3. Một quy tắc nhớ lâu

Static policy trước; volatile context sau; tool schema ngoài prose; compaction tách riêng.

Quy tắc này không phải specification. Nó là heuristic rút ra từ ba source: Pi cho thấy cách ghép string có gate; OMP cho thấy block order và cache-aware context; OpenCode cho thấy provider selection và tool contract tách khỏi text.

Để xem bản nén có thể in được, mở Prompt assembly quick reference. Bản đầy đủ có trong research note.

4. Tự kiểm tra — trả lời trước khi xem feedback

Chọn một đáp án cho mỗi câu. Mỗi lựa chọn cố ý có cùng bốn từ; hãy tập trung vào ý nghĩa, không vào độ dài.

1. OMP gần với mô hình nào?

2. OpenCode gửi tool schema ở đâu?

3. Pi customPrompt thay thế gì?

Next step

Hãy trả lời bằng trí nhớ: nếu thêm AGENTS.md vào Wincode, bạn sẽ đặt nó ở base, context hay tool contract — và vì sao? Gửi câu trả lời hoặc câu hỏi follow-up cho tôi; tôi sẽ dùng nó để thiết kế bài tiếp theo và xác định phần nào đã thành kiến thức bền.
