## Executive comparison

Pi, OMP, and OpenCode all separate a durable or mostly-static instruction base from runtime data, but they choose different seams:

- **Pi** builds one string in `buildSystemPrompt()`. Its inline default prose is combined with tool snippets, conditional guidelines, append text, project context files, skills, and the current working directory. A custom prompt replaces the default prose but still receives append text, context files, skills (when `read` is available), and cwd. [`packages/coding-agent/src/core/system-prompt.ts`, `buildSystemPrompt`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/system-prompt.ts#L1-L160)
- **OMP (Oh My Pi)** keeps substantial static text in imported Markdown/Handlebars templates, then asynchronously prepares dynamic data and returns an ordered array of provider-facing system blocks. The default/custom instruction block is followed by optional computer-safety, project/environment, and active-repository blocks. [`packages/coding-agent/src/system-prompt.ts`, `buildSystemPrompt`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/system-prompt.ts#L680-L1040)
- **OpenCode** selects a provider/model-specific static `.txt` prompt, then prepends dynamic environment/instruction/MCP/skill blocks in the request-preparation layer. Tool definitions and schemas travel separately as the AI SDK `tools` object rather than being rendered as a textual inventory by the system prompt. [`packages/opencode/src/session/llm/request.ts`, `prepare`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/llm/request.ts#L50-L111), [`packages/opencode/src/session/tools.ts`, `resolve`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/tools.ts#L50-L116)
- **Wincode** currently has a deliberately small composition root: `buildAgentTurn()` combines a fixed base instruction with the resolved agent's instruction string; tools are carried as a separate `tools` collection. Skill activation is represented as an additional user message, not by appending the skill body to the system string. [`apps/cli/src/modules/conversations/hooks/runtime-turn.ts`, `buildAgentTurn`](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/hooks/runtime-turn.ts#L658-L710)

These are source facts. Recommendations for Wincode are explicitly labeled **[INFERENCE]** below.

## Composition order and architecture

### Pi

`BuildSystemPromptOptions` exposes the composition inputs: an optional replacement `customPrompt`, selected tool names and one-line `toolSnippets`, extra `promptGuidelines`, an `appendSystemPrompt`, cwd, pre-loaded context files, and pre-loaded skills. [`system-prompt.ts`, `BuildSystemPromptOptions`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/system-prompt.ts#L6-L34)

The default path is ordered as follows:

1. Inline role/instructions and `Available tools`; only tools with a supplied snippet are rendered in that textual list.
2. Conditional file-exploration guidance, caller-provided guideline bullets (deduplicated), then the always-present concise-response and file-path bullets.
3. Inline Pi documentation guidance.
4. `appendSystemPrompt`, if non-empty.
5. `<project_context>` containing each pre-loaded context file as `<project_instructions path="...">`.
6. Skills, but only when `read` is available.
7. `Current working directory: ...`.

The ordering and gates are implemented directly in `buildSystemPrompt()`: tool visibility is snippet-driven, guidelines are deduplicated, append text is added before context, context precedes skills, and cwd is last. [`system-prompt.ts`, default/custom branches](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/system-prompt.ts#L36-L160)

When `customPrompt` is present, Pi does **not** render the default role, tool-policy, or documentation text. It starts with the custom string, then applies the same append/context/skill/cwd tail; skills are gated by `selectedTools` containing `read`. [`system-prompt.ts`, custom branch](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/system-prompt.ts#L41-L76)

The runtime rebuilds that prompt from resource-loader values and the currently valid active tool names. `_rebuildSystemPrompt()` collects tool snippets and tool guidelines, then passes loaded skills, context files, custom system prompt, append system prompt, selected tools, and cwd to `buildSystemPrompt()`. [`packages/coding-agent/src/core/agent-session.ts`, `_rebuildSystemPrompt`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/agent-session.ts#L1065-L1100)

Pi's context-file loader checks one candidate in the agent directory and then walks cwd ancestors, inserting ancestor files root-first. Candidate names are `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, and `CLAUDE.MD`; a linked-worktree shadowing rule prevents loading the main repository's logically duplicated file twice. [`packages/coding-agent/src/core/resource-loader.ts`, context loading](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/resource-loader.ts#L71-L156)

Pi's Markdown prompt-template loader is a separate feature: it discovers global/project/explicit `.md` templates and expands slash-command input such as `/name args`; those templates are not automatically merged into the system prompt. [`packages/coding-agent/src/core/prompt-templates.ts`, `loadPromptTemplates`/`expandPromptTemplate`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/prompt-templates.ts#L104-L239)

### OMP

OMP's static instruction surfaces are separate files: `prompts/system/system-prompt.md` is the default, `custom-system-prompt.md` is selected when `SYSTEM.md`/`--system-prompt` is active, and `project-prompt.md` is a separate project/environment footer. The customization documentation names these files and the primary builder symbols. [`docs/system-prompt-customization.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/docs/system-prompt-customization.md#L1-L16)

The default template contains the role, engineering/runtime conventions, skills/rules sections, internal-URL catalog, tool inventory/policy, delegation gates, workflow, verification, cleanup, delivery, and completeness rules. Most sections are conditional Handlebars blocks keyed by dynamic data such as `skills`, `rules`, `toolInfo`, `toolRefs`, feature flags, and `personality`. [`prompts/system/system-prompt.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/prompts/system/system-prompt.md)

The custom template starts with optional system-prompt customization, custom text, and append text; then renders context/git content, skills, always-apply rules, domain-rule metadata, and optional secret-redaction guidance. It therefore changes the default instruction base without discarding generated context, skills, or rules. [`prompts/system/custom-system-prompt.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/prompts/system/custom-system-prompt.md), [OMP customization semantics](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/docs/system-prompt-customization.md#L31-L80)

The project footer is intentionally a separate block. It renders workstation data, model, `<repo-rules>` context files, deeper-directory pointers, optional workspace tree/additional roots, critical execution rules, and append text. [`prompts/system/project-prompt.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/prompts/system/project-prompt.md)

`buildSystemPrompt()` prepares dynamic inputs concurrently, with a five-second preparation deadline and minimal fallbacks. It loads custom/append prompt input, context files, skills, workspace tree, active-repository context, CPU/GPU information, and personality before rendering. [`system-prompt.ts`, preparation](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/system-prompt.ts#L681-L879)

At render time OMP derives tool names, tool aliases, tool inventory metadata, filtered skills, deduplicated always-apply rules, workspace-tree data, model/personality/feature flags, and other template variables. If inline descriptors are disabled and native tool calling is active, it uses compact tool-name mode; otherwise it renders `renderToolInventory()` into the prompt. It returns the rendered instruction block, optional computer-safety block, project footer, and optional active-repository block in that order. [`system-prompt.ts`, render data and result order](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/system-prompt.ts#L903-L1040)

OMP embeds an optional workspace tree in the system prompt. The tree uses depth 3, 12 children per directory, and a 120-line cap; it asks the native walker to use absolute mtimes so the rendered block stays byte-identical until files change, protecting the prompt-cache prefix. [`workspace-tree.ts`, `WORKSPACE_DEFAULTS`/`buildWorkspaceTree`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/workspace-tree.ts#L1-L87), [stable mtime rationale](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/coding-agent/src/workspace-tree.ts#L195-L229)

OMP distinguishes normal context files from sticky `RULES.md`: context files are injected in the opening project block, while native `RULES.md` is an always-apply rule re-attached near the current turn. Its context documentation also specifies provider priorities, depth shadowing, and farther-ancestor-first injection order. [`docs/context-files.md`, load/injection behavior](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/docs/context-files.md#L1-L26), [`docs/context-files.md`, order and injection](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/docs/context-files.md#L93-L133)

### OpenCode

OpenCode's static base is selected by model/provider in `SystemPrompt.provider()`: Muse, GPT-4/o-series, GPT/Codex, Gemini, Claude, Trinity, Kimi, and a default prompt each map to a pinned `.txt` file. [`packages/opencode/src/session/system.ts`, `provider`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/system.ts#L1-L42)

At request preparation, an agent-specific `agent.prompt` replaces the provider-selected base; otherwise `SystemPrompt.provider(model)` is used. The dynamic `input.system` blocks are appended after that base, then an optional per-user `user.system` string is appended. The pieces are joined into one header, passed through `experimental.chat.system.transform`, and for normal providers converted into leading system-role messages. OpenAI OAuth receives the same text through `options.instructions`; workflow models receive it through `workflowModel.systemPrompt`. [`packages/opencode/src/session/llm/request.ts`, `prepare`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/llm/request.ts#L50-L111)

The live session constructs `input.system` in a fixed order: environment, discovered instructions, permission-filtered MCP instructions, skills, and an optional structured-output directive. [`packages/opencode/src/session/prompt.ts`, turn assembly](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/prompt.ts#L1252-L1286)

`SystemPrompt.environment()` provides model identity, cwd, worktree, git status, platform, current date, and available project references. `SystemPrompt.skills()` provides verbose skill descriptions plus a directive to load matching skills with the skill tool. `SystemPrompt.mcp()` emits `<mcp_instructions>` blocks only for MCP instructions whose tools are not all permission-disabled. [`packages/opencode/src/session/system.ts`, dynamic services](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/system.ts#L45-L111)

Instruction discovery is a separate service, not a hard-coded paragraph in the static prompt. It checks a global `AGENTS.md` and (unless disabled) `~/.claude/CLAUDE.md`; project discovery searches upward for the first matching filename among `AGENTS.md`, `CLAUDE.md`, and deprecated `CONTEXT.md`; configured local globs and HTTP(S) instruction URLs are also loaded. The service formats each loaded source as `Instructions from: <path-or-url>\n<content>`. [`packages/opencode/src/session/instruction.ts`, `systemPaths`/`system`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/instruction.ts#L110-L174)

OpenCode also resolves nearby instruction files lazily when the model reads a file: `Instruction.resolve()` walks upward from the read target, skips already-loaded/system paths, and attaches each nearby file at most once per assistant message. [`instruction.ts`, `resolve`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/instruction.ts#L183-L223)

Tool descriptions and schemas are separate from the textual system base. `SessionTools.resolve()` turns every permitted registry definition into an AI SDK tool with `description`, transformed input schema, and an executor; the registry's built-ins include `read`, `glob`, `grep`, `shell`, `edit`, `write`, `task`, and others. [`packages/opencode/src/session/tools.ts`, `resolve`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/session/tools.ts#L50-L116), [`packages/opencode/src/tool/registry.ts`, built-in registry](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/tool/registry.ts#L100-L118)

The model-facing tool descriptions are separate text/schema assets. For example, `read.txt` documents directory listing, pagination, and using `glob` when the path is uncertain, while `glob.ts` and `grep.ts` carry parameter descriptions and output truncation behavior. [`packages/opencode/src/tool/read.txt`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/tool/read.txt), [`glob.ts`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/tool/glob.ts#L1-L55), [`grep.ts`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/opencode/src/tool/grep.ts#L1-L45)

### Wincode at the pinned revision

Wincode's composition root defines a fixed base instruction (`BASE_AGENT_INSTRUCTIONS`) and a six-tool runtime set (`read`, `write`, `edit`, `glob`, `grep`, `shell`) plus `skill`. [`apps/cli/src/modules/conversations/hooks/runtime-turn.ts`, base/tool registry](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/hooks/runtime-turn.ts#L66-L101)

`buildAgentTurn()` converts conversation messages, optionally appends a `skill-context` **user** message containing `formatSkillUserContext(skill)`, and sets the Agent Turn's instructions to exactly `BASE_AGENT_INSTRUCTIONS` followed by `resolvedAgent.instructions`. The turn carries resolved tools separately. [`runtime-turn.ts`, `buildAgentTurn`](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/hooks/runtime-turn.ts#L646-L710)

The AI SDK adapter passes those instructions to `ToolLoopAgent.instructions` and creates each tool from its registry description/input schema. Tool-armed turns expose the resolved tools as active tools; tool-less turns use one model step. [`packages/agent-runtime-ai-sdk/src/agent-runtime.ts`, `createAgentLoop`/`toAiSdkToolSet`](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/packages/agent-runtime-ai-sdk/src/agent-runtime.ts#L467-L518)

No automatic Wincode equivalent of Pi/OMP/OpenCode's AGENTS/rules/workspace/environment aggregation appears in `buildAgentTurn()` or the AI SDK adapter: the system instruction is the base plus resolved agent instructions, while tools and activated skill context are separate inputs. This is a statement about the inspected composition path, not a claim that no other Wincode feature can supply agent instructions through configuration. [`runtime-turn.ts`, turn construction](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/hooks/runtime-turn.ts#L658-L710)

## Compaction-related prompts

Compaction prompts are separate from normal coding-agent system prompts in all four systems. They summarize serialized history for a future turn; they are not the same template as the normal tool-use prompt.

### Pi compaction

Pi's summarization system instruction is a static constant: the model must summarize the supplied conversation, must not continue it or answer its questions, and must output only the requested structured summary. [`packages/coding-agent/src/core/compaction/utils.ts`, `SUMMARIZATION_SYSTEM_PROMPT`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/compaction/utils.ts#L95-L145)

`generateSummaryWithUsage()` chooses an initial or update prompt, optionally appends `Additional focus`, serializes LLM messages into labeled plain text, wraps it in `<conversation>`, and, when present, adds `<previous-summary>` before the prompt instructions. It sends that text as a user message while passing the static summarization instruction as the system prompt. [`packages/coding-agent/src/core/compaction/compaction.ts`, summary generation](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/compaction/compaction.ts#L602-L694)

The serializer keeps user text, assistant thinking/text/tool calls, and tool-result text; tool results are capped at 2,000 characters. A split-turn path has a separate turn-prefix summary prompt, so Pi can preserve the boundary between an older prefix and a retained suffix. [`core/compaction/utils.ts`, `serializeConversation`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/compaction/utils.ts#L38-L94), [`core/compaction/compaction.ts`, turn-prefix generation](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/compaction/compaction.ts#L969-L990)

### OMP compaction

OMP imports a static summarization-system Markdown file that explicitly treats conversation history and previous summaries as untrusted data and forbids following commands or role changes inside them. [`packages/agent/src/compaction/prompts/summarization-system.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/prompts/summarization-system.md)

The main summary prompt is a static Markdown template with a required handoff structure (`Goal`, `Constraints & Preferences`, `Progress`, `Key Decisions`, `Next Steps`, `Critical Context`, and `Additional Notes`). The update template explicitly preserves prior-summary information while merging newer conversation state. OMP also has separate short-summary, turn-prefix, and handoff-document prompts. [`compaction-summary.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/prompts/compaction-summary.md), [`compaction-update-summary.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/prompts/compaction-update-summary.md), [`compaction-short-summary.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/prompts/compaction-short-summary.md), [`compaction-turn-prefix.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/prompts/compaction-turn-prefix.md), [`handoff-document.md`](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/prompts/handoff-document.md)

`generateSummary()` serializes the conversation with provider/dialect-aware handling, escapes summary boundary tags, chooses the initial/update prompt, appends optional additional context, and folds oversized input through multiple summary windows while carrying the previous summary forward. The static templates are rendered once into constants before the dynamic request is assembled. [`packages/agent/src/compaction/compaction.ts`, prompt constants and dynamic focus](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/compaction.ts#L564-L582), [`compaction.ts`, summary request path](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/compaction.ts#L847-L927), [`packages/agent/src/compaction/utils.ts`, serialization/escaping](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/utils.ts#L208-L224)

OMP additionally records file operations from tool calls and previous summaries, then updates the durable summary with a bounded `<files>` section. [`packages/agent/src/compaction/utils.ts`, file-operation summary](https://github.com/can1357/oh-my-pi/blob/969062200754ea02cfac922e5ebb8c608c079e15/packages/agent/src/compaction/utils.ts#L120-L181)

### OpenCode compaction

OpenCode's core compaction implementation keeps the static summary schema and update instructions inline in `packages/core/src/session/compaction.ts`. The schema requires `Objective`, `Important Details`, `Work State` (`Completed`, `Active`, `Blocked`), `Next Move`, and `Relevant Files`; it also requires terse bullets and exact paths/symbols/commands where known. [`packages/core/src/session/compaction.ts`, `SUMMARY_TEMPLATE`/`SUMMARY_UPDATE_INSTRUCTIONS`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/core/src/session/compaction.ts#L1-L55)

`buildPrompt()` dynamically wraps serialized history in `<conversation>`. For a first compaction it asks for a new anchored summary; for later compactions it adds `<prior-summary>` and explicit merge instructions before the same template. [`packages/core/src/session/compaction.ts`, `buildPrompt`](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/core/src/session/compaction.ts#L137-L174)

The serializer emits user text, assistant text/reasoning/tool calls, tool results/errors, system updates, synthetic context, and shell output; tool output is capped at 2,000 characters. The compaction request sends a single user message containing the built prompt, no tools, and a maximum summary output of 4,096 tokens. [`packages/core/src/session/compaction.ts`, serialization](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/core/src/session/compaction.ts#L83-L120), [`compaction.ts`, summary request](https://github.com/anomalyco/opencode/blob/10765ff2a9da8c3b88e4de873aa383a49c318912/packages/core/src/session/compaction.ts#L176-L229)

OpenCode's compaction selection keeps a configurable recent-token tail (default 8,000), reserves a 20,000-token buffer for overflow decisions, and excludes existing compaction entries from serialized conversation selection. ### Wincode compaction at the inspected revision

Wincode's compaction system instruction is the static `COMPACTION_SUMMARY_SYSTEM_PROMPT`: it asks for a concise plain-text maintenance summary that preserves requests, decisions, current work, unresolved errors, identifiers, paths, and tool call/result pairings, while treating historical attachments as metadata. [`apps/cli/src/modules/conversations/compaction/summary-generator.ts`, constant](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/compaction/summary-generator.ts#L21-L31)

`buildSummaryPrompt()` dynamically adds public focus, an optional prior durable summary, and either a serialized transcript fallback or separate summary messages. `summaryPromptMessages()` drops system-role messages and converts each remaining message to a user/assistant runtime message using `serializeMessagesForCompaction()`. The generator sends the static system instruction plus either one user `prompt` or a user prompt followed by these messages. [`summary-generator.ts`, dynamic request construction](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/compaction/summary-generator.ts#L48-L114)

The canonical transcript serializer preserves message id, role, selected agent/model metadata, text, and bounded attachment metadata; it omits attachment payloads and caps oversized serialized parts. [`apps/cli/src/modules/conversations/compaction/compaction.ts`, `serializeMessagesForCompaction`](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/compaction/compaction.ts#L347-L384), [handoff context for the compaction implementation](https://github.com/sonwjnn/wincode/blob/70016f33315365e35c9c8dc07391f1430c409afb/apps/cli/src/modules/conversations/compaction/summary-generator.ts#L21-L114)

The current compaction path therefore already has a useful separation between static summary policy, dynamic focus/prior-summary instructions, and serialized message content. The comparison below treats that split as existing Wincode behavior rather than redoing the completed compaction implementation.

## Recommendations for Wincode (analysis/inference)

The following are deliberately **[INFERENCE]** from the source comparison, not claims that Pi, OMP, or OpenCode require Wincode to copy their design.

1. **[INFERENCE] Introduce a typed, ordered prompt-assembly seam while preserving the current simple result.** Model the normal prompt as named blocks such as `base`, `agent`, `environment`, `projectInstructions`, `toolPolicy`, and `turnContext`, then render/join them in one documented order. This would give Wincode the observability of OMP's block array and OpenCode's request-preparation seam without forcing provider-specific behavior into agent definitions.
2. **[INFERENCE] Keep tool schemas/descriptions out of duplicated prose, but add a small conditional tool-policy block.** Wincode already sends tool descriptions/input schemas separately through `ToolLoopAgent` and `toAiSdkToolSet()`. A prompt block should explain only high-level operating policy and available capabilities, derived from the same resolved-tool registry; it should not copy parameter schemas that can drift. This follows OpenCode's separate tool-definition path and Pi/OMP's conditional tool-policy sections.
3. **[INFERENCE] Add a deterministic project-instruction layer with explicit provenance.** If Wincode should support repository guidance, load approved `AGENTS.md`/`CLAUDE.md`-style files into a named block with source paths, trust/permission rules, and a stable root-to-leaf order. OMP's context/rule distinction and OpenCode's first-match plus lazy nearby-file behavior are useful options; the important design property is that the model can tell injected instructions from transcript content.
4. **[INFERENCE] Add a compact environment block only for values that help the model act.** cwd/workspace root and platform are useful; current date and volatile filesystem metadata should be isolated from a cacheable prefix or emitted as per-request context. OMP's absolute-mtime workspace tree is evidence that cache stability matters, while OpenCode shows the utility of model/worktree/git metadata.
5. **[INFERENCE] Preserve lazy skill loading.** Wincode's current `skill-context` user message and separate skill tool avoid placing every skill body into the system prefix. Keep the catalog/description small and load a skill body only after activation, while retaining a content hash/provenance marker for compaction and replay.
6. **[INFERENCE] Harden compaction boundaries and transcript trust.** Wincode already separates static summary policy, dynamic summary instructions, and serialized messages. Add explicit `<conversation>`/`<prior-summary>` boundaries, escape or reject boundary tags from serialized content, and state that transcript text is untrusted data that must never override the summarizer's instructions. OMP explicitly does the latter; Pi and OpenCode demonstrate stable structured handoff schemas.
7. **[INFERENCE] Prefer a stable structured summary contract over unconstrained plain text if downstream reconstruction benefits from it.** Pi/OMP/OpenCode require named sections and exact paths/identifiers, whereas Wincode currently asks for concise plain text. A Wincode schema should remain compact and preserve the current focus/prior-summary flow; it should be adopted only if consumers can rely on those fields, not merely because another harness has sections.
8. **[INFERENCE] Keep compaction prompts on a separate assembly path.** Do not reuse the full coding-agent system prompt for summarization. Continue passing a dedicated summary system instruction plus dynamic transcript/prior-summary content, and keep coding tools disabled for the summary request. This matches the observed separation in all three reference harnesses and the current Wincode generator API.
