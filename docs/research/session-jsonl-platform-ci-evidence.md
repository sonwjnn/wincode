# Session JSONL native-platform CI evidence

## Findings

### Codex's relevant CI pattern

Codex separates target builds from native tests. Its full Rust workflow has per-platform test jobs that call a reusable Nextest workflow: a platform archive is built, then tests run in four shards on the selected platform runner. The full path includes native Linux x64/ARM64 and Windows x64/ARM64 tests, and macOS ARM64 tests; Windows ARM64 tests run natively even when their archive is built on Windows x64. Some jobs use Codex-managed runner groups, so the useful precedent is native test execution and per-platform reporting, not copying its runner labels ([full workflow](https://github.com/openai/codex/blob/main/.github/workflows/rust-ci-full.yml), [reusable platform workflow](https://github.com/openai/codex/blob/main/.github/workflows/rust-ci-full-nextest-platform.yml)). The full path is called by Codex's post-merge workflow; the Bazel PR path uses a different, faster mix and reserves native Windows tests for post-merge runs ([post-merge workflow](https://github.com/openai/codex/blob/main/.github/workflows/postmerge-ci.yml), [Bazel workflow](https://github.com/openai/codex/blob/main/.github/workflows/bazel.yml)).

The useful pattern here is native execution on each OS, not Codex's Rust-specific archive/shard machinery. GitHub's matrix strategy creates a job for each declared configuration, and `fail-fast: false` lets the other platform jobs finish after one fails ([matrix docs](https://docs.github.com/en/actions/using-jobs/using-a-matrix-for-your-jobs)).

### What this repository's matrix establishes

The worktree's `.github/workflows/ci.yml` now has a `session-storage-platform` matrix for Linux x64, Linux ARM64, and Windows x64. Each leg verifies `process.platform`/`process.arch` and `Bun.version === "1.4.4"`, then runs the cross-process lock tests, JSONL codec/SDK tests, durable path-publication contract tests, attachment-store tests, and bundle export/import/fork tests. The SDK suite includes a contract test that waits for `FileHandle.sync()`, terminates the worker before acknowledgement, then reopens the Session and verifies duplicate replay without a second provider request. The workflow gate checks that the matrix job succeeds.

This is actual native-runtime test coverage for those three targets when the workflow completes; a successful build on another OS would not substitute. It does not exercise the Darwin lock adapters, measure performance, or simulate host/power loss. The workflow gate itself waits for the platform matrix. A GitHub API check on 2026-11-03 returned `Branch not protected` for `master` and no repository/inherited rulesets, so merge protection does not currently require this gate.

### OS and durability limits

#### Windows path durability worktree patch

The initial native Windows Session-storage run failed because syncing a directory handle returned `EPERM`. Commit `33bebbbf` replaced directory-handle sync with same-volume `MoveFileExW` publication using `MOVEFILE_WRITE_THROUGH` (plus `MOVEFILE_REPLACE_EXISTING` only for replacement). Marker removal first moves the authoritative name into an ignored `.removed` cleanup directory with the same write-through flag; session-log removal remains cleanup behind the durable deletion marker. Temporary directory names are excluded from Session discovery.

The Windows run for `33bebbbf` exposed a second issue: existing JSONL marker/log/receipt files were reopened read-only before `FileHandle.sync()`, which also returned `EPERM`. Commit `763a7680` opens those existing files with `r+` on Windows, giving `FlushFileBuffers` the required `GENERIC_WRITE` handle. Its native run `41586772615` passed all four Windows durable-path contract tests, but the expanded Session-storage suite failed while recursively removing temporary test roots (`EBUSY`). Commit `4ee110cd` added bounded cleanup retries, but run `41588029666` reproduced the same 35 cleanup failures. Diagnostics in run `41589119866` showed that failed roots retained both SQLite databases with their `-wal`/`-shm` sidecars, plus the workspace. The affected fixtures use Bun SQLite's default non-throwing `close()`, which can defer connection release until statements are finalized or collected. Commit `a904ac84` forces Bun GC on Windows after fixture teardown and before deleting roots, collecting those deferred statement finalizers; native run `41590148790` passed the complete Session-storage suite on Windows x64, as well as Linux x64 and Linux ARM64. The final-head run `41591022522` repeated all three successful matrix legs. This validates the tested runner/filesystem paths and process-crash coverage, not power loss or every storage stack. The retries were removed because they did not resolve the issue. Microsoft documents that `MOVEFILE_WRITE_THROUGH` does not return until the file is moved on disk, and explicitly guarantees flushing for copy-and-delete moves; the implementation stages paths on the same volume so it does not request that non-atomic cross-volume fallback ([`MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)). Microsoft requires `GENERIC_WRITE` on a handle passed to `FlushFileBuffers` ([`FlushFileBuffers`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)). These API guarantees still depend on the filesystem and storage stack honoring flushes. The local contract tests do not simulate power loss; do not claim universal power-loss guarantees.

- Linux `flock()` is advisory; locks are associated with an open file description and are released when its file descriptors are closed. Linux's documentation also describes NFS/SMB behavior that can differ from local filesystems, so a GitHub-hosted runner does not prove behavior on every network filesystem ([Linux `flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html)).
- Windows `LockFileEx` provides exclusive byte-range locks. Windows documents that locks are released when the owning process terminates, but the time to release can depend on system resources ([Microsoft `LockFileEx`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)). The cross-process contention and process-exit tests are therefore the relevant native checks.
- Bun documents `FileHandle.sync()` as a request to flush file data to storage; its implementation is OS/device-specific ([Bun API reference](https://bun.com/reference/node/fs/promises/FileHandle/sync)). The crash test covers a synced record followed by process termination, not power loss, controller caches, or all storage devices.
- The crash test calls `Bun.spawn`'s child `.kill("SIGKILL")`. Bun's tagged v1.4.4 test suite also exercises `Subprocess.kill("SIGKILL")` without excluding Windows, which supports API availability but does not replace running this repository's test on Windows ([Bun v1.4.4 test](https://github.com/oven-sh/bun/blob/bun-v1.4.4/test/js/bun/spawn/spawn-kill-signal.test.ts)).
- The lock tests create symlinks and hard links. Microsoft says unprivileged symlink creation requires Developer Mode; GitHub's hosted-runner reference says Windows VMs run as administrators with UAC disabled. This makes the hosted runner plausible for the symlink test, but the actual Windows leg remains the evidence ([Microsoft `CreateSymbolicLinkW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinkw), [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)).
