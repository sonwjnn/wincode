## Findings

| Upstream / state | Does a report interrupt or inject into active work? | Does an idle parent start automatically? | Does a cold process restart replay the pending report automatically? |
|---|---|---|---|
| **OMP, owning session live and parent active** | **No mid-request injection.** Completion is queued as an `async-result` aside and surfaced by the parent loop at a work-step/tool-batch boundary; foreground tools keep running. | N/A | N/A |
| **OMP, owning session live and parent idle** | N/A | **Yes, conditionally.** The live session's yield queue flushes to `AgentSession.injectIdle`, which prompts a follow-up turn without UI input. A missing live sink is dead-lettered. | N/A |
| **OMP, process restarted** | — | — | **No automatic report replay is evidenced.** Jobs, sinks, and queues are process-local; persisted child transcript/session rows can be inspected or explicitly revived, but revival is not a delivery replay. External supervisors are outside this source evidence. |
| **Codex MAv2, parent active** | **Not an interrupt.** A terminal completion is queue-only (`trigger_turn=false`). The loaded parent queues it; the running loop can consume it before a later model request at an allowed step boundary, not inside the in-flight provider request/tool continuation. `wait_agent` observes mailbox activity but returns a summary, not the completion text. | N/A | N/A |
| **Codex MAv2, parent idle** | N/A | **No, ordinarily.** The completion message does not trigger a turn; the handler starts pending work only for `trigger_turn` input or an outstanding durable sleep. Unloaded-thread mail can remain in the same live runtime until that thread is loaded. | N/A |
| **Codex MAv2, cold process restart** | — | — | **No automatic replay/resumption is evidenced by Core.** The completion mailbox is runtime memory, is closed on shutdown, and a fresh runtime starts with an empty mailbox. V2 resume restores the requested thread/runtime on demand, not pending completion delivery. An external host could add behavior not shown here. |

## Codex source trace

1. **Terminal child outcome becomes a queue-only report.** `notify_parent_of_terminal_turn` formats the final status/result as an `InterAgentCommunication` with `trigger_turn=false`, then sends it to the parent; `AgentControl::turn_finished` delegates to that path. [completion routing](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/agent/control/completion.rs#L25-L110) [turn-finished hook](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/agent/control/api.rs#L300-L334)

2. **Loaded versus unloaded parent routing.** A non-triggering message to an unloaded thread is put in the runtime mailbox; a loaded recipient receives an `Op::InterAgentCommunication`. The session handler enqueues that communication, and calls the pending-work turn starter only when `trigger_turn` is true or the session has a durable sleep. Since completion reports have `trigger_turn=false`, ordinary idle completion does not start a turn. [control delivery routing](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/agent/control.rs#L250-L345) [session queue/start policy](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/session/handlers.rs#L55-L82)

3. **Active-parent boundary.** `run_turn` drains pending input only when its `can_drain_pending_input` gate permits, records drained messages before building the next model request, and explicitly defers draining at turn start and while a model/tool continuation is pending. `RegularTask` checks for pending input after `run_turn` and continues processing when any remains. Thus completion may reach a later request boundary in the active task; it does not cancel the current provider request or tool call. [model-request boundary](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/session/turn.rs#L380-L500) [regular-task continuation](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/tasks/regular.rs#L45-L98)

4. **`wait_agent` is activity-only, not a report-return API.** Its V2 description says it waits for mailbox updates and returns a summary, not content; implementation subscribes to the parent's input-queue activity and returns `Wait completed.` for mailbox activity. [V2 wait contract](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/tools/handlers/multi_agents_spec.rs#L235-L265) [wait implementation/result](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/tools/handlers/multi_agents_v2/wait.rs#L45-L190)

5. **Same-process unloaded-thread retention is not restart durability.** `LocalAgentRuntime` owns a `Mailboxes` instance initialized with `Arc::default()`; `Mailboxes` is a `Mutex<Option<HashMap<ThreadId, Mailbox>>>`. It retains queue-only mail for unloaded threads within that runtime, but shutdown calls `close`, which takes/drops the map. A new runtime begins with a fresh empty map. [runtime allocation/shutdown](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/agent/control/runtime.rs#L105-L208) [mailbox storage/close](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/agent/control/mailbox.rs#L12-L105)

6. **V2 cold resume is demand-driven and does not replay completion.** `resume_agent_from_rollout` resumes the requested thread; for MAv2 it returns before the legacy descendant-resume traversal. `resume_single_agent_from_rollout` attaches a completion watcher only for non-V2 agents, so resuming a completed V2 child does not, by itself, re-emit its prior completion report. [resume behavior](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/agent/control/spawn.rs#L1240-L1315) [resumed-thread watcher condition](https://github.com/openai/codex/blob/afb436df8b70bb5bc57b86d9a3e829968988cd21/codex-rs/core/src/agent/control/spawn.rs#L1405-L1475)

## OMP source trace

1. **Live parent delivery is an aside at a safe loop boundary.** The async task contract promises auto-delivery. Completion marks the job complete and queues its result; the owning `AgentSession` enqueues an `async-result` in its yield queue, exposed as an aside. The agent loop checks asides between work steps and drains them at tool-batch/stop boundaries. Background completion peeking does not inject into an executing provider/tool call; only interruptible waits can be interrupted. [async contract](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/prompts/tools/task-async-contract.md#L1-L6) [job completion](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/async/job-manager.ts#L418-L422) [owner enqueue](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/session/agent-session.ts#L2791-L2814) [aside provider](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/session/agent-session.ts#L1813-L1818) [loop boundaries](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/agent/src/agent-loop.ts#L1770-L1805) [tool batch/wait behavior](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/agent/src/agent-loop.ts#L3306-L3334)

2. **Live idle parent auto-starts a follow-up.** YieldQueue schedules an idle flush; `AgentSession.injectIdle` injects via `agent.prompt(...)`. This depends on the owning session/sink remaining live; absent owners are dead-lettered. [idle yield scheduling](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/session/yield-queue.ts#L84-L93) [idle injection](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/session/agent-session.ts#L1763-L1793) [missing-sink handling](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/async/job-manager.ts#L151-L163) [dead-letter path](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/async/job-manager.ts#L1117-L1138)

3. **Cold process restart has no upstream report-recovery path in these sources.** Job, delivery, and sink state are process-local collections; the SDK creates its async manager singleton for the first top-level session in that process. The contract says job IDs are process-local, even though transcripts/outputs can remain readable. The Hub docs and persisted-agent reviver describe parked sessions and explicit focus/revival, not startup report replay. Therefore automatic replay after process restart is not supported by the inspected delivery path; external host/supervisor behavior is unknown. [manager state](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/async/job-manager.ts#L254-L286) [process-scoped manager](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/sdk.ts#L2113-L2132) [contract](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/prompts/tools/task-async-contract.md#L1-L6) [parked/explicit revival](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/docs/agent-hub.md#L5-L5) [revival controls](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/docs/agent-hub.md#L55-L59) [cold reviver](https://github.com/can1357/oh-my-pi/blob/6d8552d7f9df1852826923f07f0eed4fe29511f3/packages/coding-agent/src/task/persisted-revive.ts#L51-L63)

## Bottom line

OMP favors automatic delivery to a still-live owner, but only at a safe agent-loop boundary; a live idle OMP parent is prompted automatically. Codex MAv2 records completion as non-triggering mailbox input: an active turn can consume it at a later permitted sampling boundary, while an idle parent is not woken by completion alone. For both inspected codebases, the pending delivery machinery is process-local; neither source demonstrates automatic replay into the parent after a cold process restart without an explicit host/session action. For behavior outside these repositories' cited runtime paths, the evidence is unknown.
