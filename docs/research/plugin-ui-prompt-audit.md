# Prompt Audit Scope for #281 Plugin UI

**Status:** This is a research recommendation, not an approved Prompt Audit instruction. The exact live instruction was not present in the supplied context. I searched repository text, local project session/subagent task-review artifacts, #281 and its comments, and PR #294's description/reviews; no separate exact instruction surfaced. The scope below is therefore explicitly **proposed**.

## Confirmed from first-party sources

- **#281:** The issue asks for keyed status/widgets, title and other presentation controls, ordered display-only Markdown transforms, and explicitly excludes changing stored payloads or model-context inclusion as a side effect of rendering. Its Testing Decisions call for preserving stored content under Markdown transforms. See [User Stories](https://github.com/sonwjnn/wincode/issues/281#user-stories), [Implementation Decisions](https://github.com/sonwjnn/wincode/issues/281#implementation-decisions), [Testing Decisions](https://github.com/sonwjnn/wincode/issues/281#testing-decisions), and especially [Out of Scope](https://github.com/sonwjnn/wincode/issues/281#out-of-scope).
- **ADR-0058:** Plugin presentation must not change Tool Permission, Session Writer ownership, or model-context inclusion. Host mediation coordinates lifecycle; it is not a sandbox for in-process Plugin code ([ADR-0058, line 18](../adr/0058-reusable-react-tui-and-host-mediated-plugin-ui.md#L18)).
- **Accepted plan:** Message/entry renderers are presentation-only; Markdown transforms are display-only, and transformed text is explicitly never persisted or included in Session Context ([surface table and Markdown delivery](../plans/reusable-tui-and-plugin-ui.md#L112-L152); [renderer authority](../plans/reusable-tui-and-plugin-ui.md#L174-L176)). The plan separately includes composer access and custom UI results, which are potential input paths rather than display-only state.

### What the implementation routes

- In-process status/widgets are held in the Plugin UI contribution store's per-view maps/snapshots and rendered as UI; title is a separate UI snapshot. The host's update controls emit only status, widget, and title data ([store](../../packages/coding-agent/modules/plugins/ui/plugin-ui-contributions.ts#L236-L253), [status/widgets](../../packages/coding-agent/modules/plugins/ui/plugin-ui-contributions.ts#L588-L625), [update payloads](../../packages/coding-agent/modules/plugins/ui/plugin-ui-contributions.ts#L661-L688), [rendering](../../packages/coding-agent/modules/plugins/ui/plugin-ui-host.tsx#L935-L957)). These paths do not write Session Records or Session Context.
- The changed RPC path validates the same update payloads and sends them through `transport.update`; the channel emits `plugin/ui/update` as a notification, separate from Session events/messages ([RPC host](../../packages/coding-agent/modules/application/rpc/plugin-ui.ts#L349-L354), [RPC channel](../../packages/coding-agent/modules/application/rpc/plugin-ui-channel.ts#L209-L215)). The RPC integration test checks status/widget/title notifications and that an outstanding UI request does not pause the Agent ([test](../../packages/coding-agent/test/rpc-plugin-ui.test.ts#L897-L1176)).
- Markdown transformation is called by the display renderer, which passes transformed text to the Markdown renderable. The provider request and Session projections consume Session Messages, not that render output ([transformer runtime](../../packages/coding-agent/modules/plugins/runtime.ts#L879-L917), [Markdown display path](../../packages/coding-agent/modules/sessions/ui/messages/markdown-message-part.tsx#L88-L117)). Existing tests assert transformed display while the original message and active-context projection remain unchanged ([test](../../packages/coding-agent/test/application/plugin-markdown-transformers.test.tsx#L309-L430)).

### Boundaries that can carry prompt/context data

- The main turn prepares model messages from active Session Context and, for a new submission, appends the prepared user message; it commits that prompt as a Session Record ([submission preparation](../../packages/coding-agent/modules/sessions/agent-session/submission.ts#L493-L538), [prompt persistence](../../packages/coding-agent/modules/sessions/agent-session/submission.ts#L730-L785)). The turn runner then builds the request from those model messages, composed system instructions, and available tools ([turn request](../../packages/coding-agent/modules/sessions/host/agent-session-turn-runner.ts#L474-L494)).
- Durable active context is reconstructed from projected Session Messages and compaction summaries, then context edits are applied ([context projection](../../packages/coding-agent/modules/sessions/context-projection.ts#L1-L14), [Session Host load](../../packages/coding-agent/modules/sessions/host/session-host.ts#L349-L380)). Compaction is another real model boundary: it serializes Session Messages into the summary prompt and sends that prompt to the provider ([serialization](../../packages/coding-agent/modules/sessions/compaction/compaction.ts#L1553-L1562), [summary prompt](../../packages/coding-agent/modules/sessions/compaction/summary-prompt.ts#L59-L106), [provider call](../../packages/coding-agent/modules/sessions/compaction/summary-generator.ts#L519-L541)).
- **Important distinction:** `ui.setEditorText()` and paste/editor contributions intentionally affect the composer; that text becomes prompt/context only through normal submission. Dialog/custom UI values resolve back to Plugin code, not directly to Session Context. A Plugin can intentionally include a value in a Tool result or submitted user message, which then follows the ordinary model-message and Session Record path. Plugin-owned state storage is separate and is not automatically model context. The current RPC test demonstrates the Tool-result route by putting its returned UI answer into the Plugin Tool output ([public UI API](../../packages/coding-agent/modules/plugins/public.ts#L516-L552), [test handler](../../packages/coding-agent/test/rpc-plugin-ui.test.ts#L945-L980)). Thus the confirmed claim is **no automatic host routing from display state/render output**, not that arbitrary Plugin code cannot reuse the same string.

## Proposed minimal live audit

Keep the audit to direct host routing and the explicit UI-to-input seams; do not broaden it into a general Plugin sandbox or a review of arbitrary Plugin code. The following remains a recommendation, not a recovered or newly approved acceptance contract.

1. **Display-state isolation:** Put a unique sentinel only in `setStatus`, `setWidget`, and `setTitle` (and one React presentation contribution). Verify it appears in the Interactive render/RPC update as applicable, but is absent from captured provider messages/system instructions and from the durable Session Record/active context after reopen. Keep the Plugin Tool result unrelated to the sentinel.
2. **Markdown isolation:** Transform a source message to a visible sentinel. Verify the display changes while the captured provider input, stored source Session Message, and compaction serialization remain the original text. Existing renderer tests cover in-memory non-mutation; the missing evidence is an end-to-end provider/storage boundary check.
3. **Intentional-input control:** Verify composer text changes enter model input and durable context only after normal user submission. Verify a dialog/custom result alone is not auto-added; separately verify that a Plugin deliberately returning it as a Tool result is included normally. This prevents a false claim that all Plugin UI-derived text is excluded.
4. **RPC variant:** Extend the existing negotiated-UI journey to assert the sentinel-bearing `plugin/ui/update` notification is not projected into Session state or the next provider request. Retain the existing assertion that a pending request leaves Agent state `running`.

## Bounded audit work completed on the feature branch

- `plugin-ui.test.tsx` now sets unique status, widget, and title markers; computes a unique Markdown-transform output marker; submits composer text through `AgentSession.prompt`; and uses a deliberately returned test Tool result. It checks the captured provider requests, live Session Context, durable Session Records, and reopened Session Context: composer and Tool data follow their normal paths, while the display-only markers do not enter those paths. The test Tool is supplied by a test `TurnToolResolver`, not registered through the Plugin Tool API; the Plugin Tool-specific route remains unverified by this test.
- `plugin-markdown-transformers.test.tsx` now renders a unique transformed marker and checks that the original Session Message stays unchanged. This establishes the display side of the marker used by the provider-boundary test.
- Focused tests and the full Default portfolio passed. This does not cover the proposed RPC-to-provider cross-check or compaction serialization boundary, and it does not claim that Plugin code cannot deliberately reuse a UI value.

The exact live Prompt Audit instruction remains unavailable. These tests implement the user's approval to run a bounded boundary audit; they do not establish the missing instruction as an acceptance requirement.
