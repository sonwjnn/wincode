# New-session startup view research

**Scope:** research only; no source or glossary changes. The installed Pi package is `@earendil-works/pi-coding-agent` v1.2.0 at `/Users/thyhaly/.nvm/versions/node/v24.14.0/lib/node_modules/@earendil-works/pi-coding-agent` (package.json:1-4). Pi claims below are checked against its installed docs and compiled source, not a live Pi session. Wincode claims are code-based; no screenshot/runtime visual inspection was performed.

Wincode's domain instructions identify the root `GLOSSARY.md` as the fallback vocabulary source (`docs/agents/domain.md:4-8`). This note uses its terms **Agent**, **Provider Model**, **ThinkingLevel**, **Project Instructions**, **Project trust**, **Plugin**, and **Skill**. In particular, a Wincode Skill is turn-scoped, not a Plugin (`GLOSSARY.md:322-329`).

## What Pi actually puts on its startup surface

1. **Header and help.** The compact header shows a logo/version, short key hints, a disclosure hint, and onboarding copy. Expansion replaces the short hints with a fuller shortcut list; both states retain onboarding copy (`Pi/dist/modes/interactive/interactive-mode.js:713-771`). The default `app.tools.expand` key is Ctrl+O (`Pi/docs/keybindings.md:163-164`). This same expanded/collapsed state is applied to the header, loaded-resource sections, and expandable chat output (`Pi/dist/modes/interactive/interactive-mode.js:1058-1059, 3738-3753`). `--verbose` forces detail/expanded mode; `quietStartup: true` hides header and details, while `"header"` keeps only the header (`Pi/docs/settings.md:90-96`, `Pi/docs/cli.md:234-236`).
2. **Model scope, not selected model.** When a startup model scope exists, Pi prints a `Model scope:` line with model IDs and a cycling hint (`Pi/dist/modes/interactive/interactive-mode.js:662-672`). The current folder/model/context/usage/cost belong to the footer, not the resource listing (`Pi/docs/usage.md:9,25`).
3. **Loaded resource sections, only when nonempty.** Source builds compact list summaries and expanded, source-grouped details for:
   - **Context:** system-prompt source, appended system-prompt sources, and discovered instruction files; the UI lists paths, not their contents (`Pi/dist/modes/interactive/interactive-mode.js:1381-1393`).
   - **Skills:** compact names; expanded paths grouped by project, user, and path/package source (`Pi/dist/modes/interactive/interactive-mode.js:1394-1404`). Pi docs clarify that startup advertises available Skill names/descriptions/paths, not the full instructions (`Pi/docs/skills.md:43-45`).
   - **Prompts:** `/name` commands; expanded source detail (`Pi/dist/modes/interactive/interactive-mode.js:1405-1425`).
   - **Extensions:** compact labels; expanded source/path detail (`Pi/dist/modes/interactive/interactive-mode.js:1426-1432`).
4. **Resource diagnostics.** When details are shown, Pi can show Skill conflicts, prompt conflicts, extension/load/command/shortcut issues, and theme conflicts (`Pi/dist/modes/interactive/interactive-mode.js:1433-1468`). It reads themes but does **not** provide a normal `[Themes]` loaded-resource list; themes appear here only for conflicts (`Pi/dist/modes/interactive/interactive-mode.js:1349-1352, 1463-1468`). Pi's startup resource listing also does not enumerate effective tools.
5. **Scrolling and fixed editor.** The header, resource list, and chat document are children of one document container (`Pi/dist/modes/interactive/interactive-mode.js:385-391`), mounted into Pi's transcript viewport while the editor is a separate fixed viewport region (`Pi/dist/modes/interactive/interactive-mode.js:675-697`). Pi docs say fullscreen keeps editor/status fixed as the transcript scrolls (`Pi/docs/usage.md:86`). The compact-vs-expanded content is not a second screen or modal.

The current home layout centers `AsciiArt` in a `flexGrow={1}` region, followed by a non-shrinking composer/path/trust region (`new-session-view.tsx:578-628`; `ascii-art.tsx:8-40`). Wincode already uses the requested layout pattern in `ChatShell`: a full-height `scrollbox flexGrow={1}` followed by composer chrome with `flexShrink={0}` (`modules/sessions/ui/components/chat-shell.tsx:380-449`). Prefer that established pattern over inventing a scroll container. Existing home tests explicitly defend startup composer focus (`test/sessions/new-session-view-focus.test.tsx:790-798`); the AsciiArt size behavior has its own tests (`test/sessions/ascii-art.test.tsx:9-50`).

## Prioritized recommendations (proposal only)

1. **Compact summary at top-left.** Replace the centered art with a short start cue (e.g. “Describe what you want to do · `/` commands · `@` file mentions”) and the selected Agent name/one-line description. The composer already shows model/thinking; the pinned bottom already shows workspace/branch and Project trust, so do not duplicate those by default. The slash/file-mention affordances are real (`modules/sessions/README.md:166-170`).
2. **One expandable, independently scrollable resource overview.** Summary rows can show counts or short names for Project Instructions, Skills available, and Custom Commands. Expanded content can show Project Instruction source paths, Skill names/source, Custom Command `/names`, and relevant diagnostics. Hide empty sections as Pi does. Keep Plugin Tools out of the default list until Wincode can report the effective per-Agent/turn set. Use existing `scrollbox` + fixed composer pattern; start at scroll top.
3. **Preserve trust and composer behavior.** Keep the Project trust warning visible even when details are collapsed. The composer should remain fixed and receive startup focus; the expanded region should not intercept normal typing. Use semantic theme tokens and a visible, keyboard-operable expand/collapse affordance. Pi's Ctrl+O is a reference, not a Wincode keybinding decision; Wincode should check its existing composer/keyboard layers before reserving a shortcut. Avoid adding motion unless it materially communicates the expand/collapse state change.
4. **Treat asynchronous resources honestly.** Skills/Custom Commands and the Git branch resolve asynchronously. Decide whether to show a pending state, wait before displaying counts, or omit counts until ready; don't briefly claim “0” resources. On short terminals, shrink the scroll area before the composer and keep summary text wrapped/truncated safely.

## Open product decisions

- Which Agent details belong in the compact summary: name only, or name plus description/source/tools?
- Should the expandable view expose only counts/names, or source scope/path too? Should it include **Project Instructions** and their diagnostics, given they are per-turn guidance and may change before submission?
- Use “Skills available” (recommended) or expose a different state? Should Plugin Commands be listed separately from Custom Commands?
- Should warnings stay as current toasts/notices, or also appear in the expanded startup panel? Which warning must remain persistent when collapsed?
- How should async discovery appear, and does expanded/collapsed state persist for the process, view, or not at all? What visible toggle and key action avoid stealing composer input?
- Should the home view show any tool capability summary? If yes, is the product comfortable with per-Agent visible coding tools only, or should it wait for accurate per-turn Plugin Tool resolution?
