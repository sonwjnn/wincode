# Collection-owned request headers and store-owned credential rotation

An SDK Provider owns authorization, its Provider Models, and Model Protocol dispatch, but the application needs final control of chat-request headers without resolving authorization twice. A stored SDK Credential, authorization that can be resolved now, and authorization verified by an upstream service are different facts. This decision extends the independently usable Provider SDK of ADR-0048 and the Coding-Agent credential boundary of ADR-0049; issue #214 specifies the consumer-visible behavior.

Status: proposed

## Decision

- **ProviderCollection owns final chat-request headers.** After resolving authorization once for the selected Provider Model, the SDK Provider supplies Model Protocol defaults and authorization-derived headers without dispatching. The collection merges protocol defaults, auth headers, optional `Provider.headers`, `ProviderModel.headers`, and explicit `ChatRequest.headers` in that order, using case-insensitive names. It then invokes one optional asynchronous `ChatRequest.transformHeaders` and passes the finalized headers to the provider for dispatch. Public `ProviderHeaders` values are `string | null`; `null` suppresses a header at any override layer, and names are normalized after the transform too. The provider must not reintroduce a deleted or overridden default. A mixed-protocol provider chooses defaults using the selected Model Protocol. The pipeline does not apply to discovery, OAuth token exchange, or auth verification.
- **Final control is a trusted caller capability.** Explicit request headers and the transform may override credential-bearing headers. This is intentional for application gateways, not implicit substitution of the SDK Credential. Do not log secret-bearing header values; the caller remains responsible for the destination and any override. A transform failure or cancellation prevents chat dispatch and produces an observable failure or abort.
- **Configured, resolvable, and verified are separate auth questions.** `CredentialStore.list()` answers whether an SDK Credential exists without resolving its secret. `checkAuth()` means complete configured auth without OAuth refresh or a remote acceptance test; `getAuth(providerId | model)` resolves request-scoped auth, may refresh OAuth, and includes model headers for the model overload. Only a distinct explicit `verifyAuth()` may ask upstream to accept credentials; unsupported providers report that explicitly rather than sending paid inference. `getAvailable()` retains ADR-0048's *stored-credential* meaning: it lists Known Models whose registered SDK Provider has a stored credential. It does not call `checkAuth()` or `getAuth()`, consult ambient credentials, or claim that the endpoint is reachable. A Known Model remains visible after offline restore even when it is not currently Invocable. UI copy must not present saving a credential as verified connectivity.
- **The CredentialStore owns rotation atomicity.** Use cancellable `read`, non-secret `list`, serialized `modify` as the only write path, and serialized `delete` for removal. A `modify` callback returns a replacement credential or `undefined` to keep the current one; `delete` handles removal. Re-check OAuth expiry under the store lock so two ProviderCollections sharing an application store see one rotation. A persistent store shared across processes must guarantee this for file and platform-secret backends, or fail closed when it cannot acquire that guarantee. Caller cancellation before acquiring the lock or starting refresh prevents it; once upstream refresh begins, bounded completion and persistence must survive caller cancellation or the only valid rotated token could be lost. Callers may stop waiting, but the store must not discard that mutation. A refresh failure preserves the credential for explicit re-login and never silently falls back to another auth source. The default in-memory store remains isolated per collection.
- **Enumeration does not resolve secrets.** Credential listing exposes only non-secret provider/type metadata; a backing store that cannot enumerate secrets maintains a separate metadata index. Explicit `login` and `logout` use provider-owned interactions and the SDK CredentialStore; logout removes stored credentials, not upstream tokens or ambient auth. Headless requests never start interactive login. Coding-Agent preserves Provider Registration Owner isolation for Plugin credentials and does not reuse Legacy Connection Credentials.
- **Name each public operation for its effect.** Keep `ProviderCollection`, `ProviderModel`, `ChatRequest`, and `protocolId`. Use `ProviderHeaders` for the nullable header map, `headers` for static/explicit overrides, and `transformHeaders` only for the final collection-owned transform. `checkAuth()` checks whether provider authorization is configured without refreshing OAuth or verifying the remote service; `getAuth()` resolves request authorization; `verifyAuth()` optionally asks the remote service. `login()` persists a credential and `logout()` removes the stored credential. `CredentialStore.read/list/modify/delete` name the four storage operations; `modify` never deletes.

## Considered options

- **Merge headers inside each provider:** rejected because precedence, case-insensitive replacement, and deletion would differ by Model Protocol and the collection could not offer one final transform.
- **Call `getAuth()` before each chat request:** rejected because authorization could be resolved or rotated twice and the caller still could not control headers created later by the provider.
- **Treat a stored credential as verified connectivity:** rejected because storing a key and restoring Known Models involve no upstream check; verification may not be safely available for every provider.
- **Keep rotation locks only in ProviderCollection:** rejected because separate Session Hosts and processes share application-owned storage, not a collection-local queue.

## Consequences

Built-in and Plugin SDK Providers need a clear contract for producing starting headers and consuming finalized headers; their current late wire defaults cannot overwrite the transform. Application-owned credential stores need a real atomicity strategy across their intended sharing scope, plus non-secret metadata and cancellation that does not discard a started refresh. Tests should focus on the public ProviderCollection contract, with a separate persistent-store contract test for cross-collection/process atomicity; no Session schema change is required by this decision.
