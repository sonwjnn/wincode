# Minimal Plugin authoring interface

Status: accepted

A Plugin loaded from a file exports an asynchronous-capable default factory that registers Agent tools and Interactive Mode commands through a host-provided interface. Wincode publishes the registrations only after the factory completes successfully, so a failed Plugin cannot leave partially registered behavior. Plugin Tools declare Zod input schemas and return bounded text or JSON results; their Tool Permission is decided for the tool action as a whole, without a Plugin-defined resource extractor. Plugin Commands execute a handler and return text for Wincode to display. The initial interface does not include custom rendering, media or streamed tool output, Session storage, or Agent control. These capabilities were deferred to keep the public contract small and avoid exposing internal Session and UI objects to user code.

The factory runs once per process. A Plugin may handle each Session's start and shutdown, and process shutdown; cleanup is idempotent. Its tools may be visible to Primary Agents and Subagents, with the effective Tool Permission evaluated for the calling Agent. A Tool handler error becomes a failed Tool Call, a Command handler error becomes a user-visible error, and a Session start failure disables the Plugin for that Session without disabling other Sessions. Code changes take effect after Wincode restarts; the initial interface has no hot reload.

Session start and shutdown follow each loaded Session runtime, not the full lifetime of its durable Session. An idle runtime may unload and later reopen the same Session, yielding a new pair of lifecycle calls; Plugin memory associated with the prior runtime is not restored by Wincode.

Plugin authors import the narrow authoring contract from the stable `@wincode/coding-agent/plugin` subpath, which maps directly to `packages/coding-agent/modules/plugins/public.ts`; a separate `plugin/` barrel directory is unnecessary. `packages/coding-agent/plugins/` contains Wincode-owned built-in integrations. Their MCP and Subagents adapters use the `@wincode/mcp` and `@wincode/subagents` domain packages, respectively; those packages do not depend on the Coding-Agent Plugin API. `packages/coding-agent/modules/application/plugins/registry.ts` is the adapters' tool-provider registry, configured by built-in Plugin factories; it also accepts the Session Delegation runtime factory. `packages/coding-agent/modules/plugins/` contains the separate loader, runtime, and public contract for file-loaded Plugins. The dedicated loader may use Bun `require(path)` for an explicitly enabled TypeScript file; the repository's top-level import rule remains in force elsewhere.

Plugin Tools retain the Agent Runtime's parallel Tool Call semantics; Plugin authors coordinate shared mutable state inside their handlers. A Plugin Command may appear before a Session is opened, so its context has an optional Session identity. In Print and JSON Modes, a Plugin Tool whose effective decision is `ask` fails closed until an explicit rule allows it. The public authoring entry is shipped with installed Wincode, rather than requiring a separate Plugin SDK package in the initial release. A sample `jira` Plugin with a `search_issues` tool and `/open-issue` command serves as the first end-to-end contract check.
