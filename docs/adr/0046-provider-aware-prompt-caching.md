# Provider-aware prompt caching stays separate from Session Context

Provider prompt caching reuses provider-side processing of a matching prefix; it does not shorten the model's context, which remains the concern of Session Compaction. This decision describes the SDK Provider caching contract for Anthropic, OpenAI, Google, and OpenCode Go. The Provider SDK implementation is carried by ADR-0049.

Status: accepted

## Decision

- **Provider Model metadata owns cache capabilities.** Each Provider Model declares supported cache modes, retention tiers, and relevant eligibility limits. SDK protocol implementations serialize cache controls and normalize provider usage. OpenCode Go follows the selected model's actual protocol, not the connection-provider ID.
- **Policy is scoped to exact Provider Model identity.** Use a global short-retention default with per-model overrides keyed by `{ providerId, modelId }`, constrained by the selected Provider Model's declared capability. `off` disables cache directives, explicit resources, keys/retention controls, and warming that Wincode initiates. This is best-effort: OpenAI and Gemini may still apply provider-managed implicit caching, which Wincode cannot reliably disable. An OpenAI `prompt_cache_key` is a routing/accounting hint, not a security boundary.
- **Provider-specific behavior remains distinct.** Anthropic uses explicit `cache_control` breakpoints on stable prefixes. OpenAI uses only controls and retention values supported by the selected Provider Model; where supported, `prompt_cache_key` is stable per Session. Google has a separate `CachedContent` resource manager for explicit caching: cache stable system instructions and tool schemas, not changing conversation history; identify resources by Session, exact Provider Model identity, cacheable-prefix fingerprint, selected TTL, and authorization identity; delete on prefix or selection change and Session close. TTL is the crash-cleanup fallback. Google implicit caching is observed through usage, not controlled by Wincode. Google resources are not synthetically warmed or automatically extended.
- **Warming is streaming-only and economic.** For a route whose cache lifetime can be refreshed by a model request, refresh only while its Stateful Agent remains active and the request can be replayed with the same prompt-affecting options. Schedule near 90% of TTL while keeping a 10-second margin; stop after one hour from the real request. Warm only when known pricing predicts at least $0.05 in savings; use at most one output token, no retries, and one warmer per Session. Keep it scheduled across idle Agent Turns while the Session Host's Stateful Agent remains loaded; replace it when a new real request starts. Cancel on stable-prefix or exact Provider Model identity change, Session close, or Host/Stateful Agent shutdown—not merely when one Agent Turn completes. Appended messages and the active assistant stream do not invalidate the captured prefix; truncation, rewriting, or compaction does. Warming and resource failures never fail the active Agent Turn. Compaction-summary requests do not use cache controls or warming.
- **Usage is canonical and separate from conversation.** `ModelUsage.inputTokens` means total input tokens, including cached reads and writes; `cacheReadTokens` and `cacheWriteTokens` are breakdowns within that total. Anthropic's `input_tokens` must therefore be normalized together with its cache-read and cache-creation fields; OpenAI and Google totals are preserved according to their protocol contracts. Cost calculation prices uncached, cached-read, and cache-write portions separately, while context and compaction use the full input total. Persist warm spend as a separate Session Usage Entry, not a Session Record or message; include it in Session cost/UI, but never in Session Context or Session Transcript.
- **Cache failure is an optimization failure.** For a cache-specific rejection before any output, retry once without cache controls or the explicit resource. Do not retry unrelated provider errors or errors after output begins.

## Consequences

Provider Model metadata, its schema, and generator overlays carry cache capabilities; generated provider-scoped metadata remains generated and is not edited directly. Session persistence and Session Usage Entries keep warming spend distinct from conversation usage, and the Session surface can show cached reads/writes and warming state. Database schema changes follow the repository's direct Drizzle synchronization policy. Contract tests protect total-context accounting, provider-specific request serialization and routing, cache-specific fallback, Google resource cleanup, summary-request opt-out, and the rule that warming usage affects cost but not conversation context.
