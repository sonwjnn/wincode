# Stateful Agent owns live conversations; delegated work has durable child Sessions

Status: accepted

`@wincode/agent-core` owns a Stateful Agent for one loaded conversation across Agent Turns: live context and scheduling, lifecycle events, tool execution, approval settlement, and the steering/follow-up queues. `@wincode/coding-agent` owns Session Records, storage, Tool Permission and compaction policy, attachments, presentation, and process-level runtime management. The coding-agent Agent Session connects these boundaries without becoming a second live-state writer. This replaces the live-ownership and view-bound lifetime choices in ADR-0019, ADR-0023, ADR-0031, and ADR-0032; their unchanged input and persistence contracts remain in force. Moving the whole coding-agent session into core was rejected because it would pull storage and application policy into the reusable runtime; retaining two live-state owners would recreate the races those decisions addressed.

## Delegation and lifetime

Each delegated task has a stable Task ID and its own durable child Session ID linked to the parent Session, Turn, and Tool Call. The child has a separate Stateful Agent and context initialized from explicit task and instructions, not an automatic copy of the parent's transcript. Spawning returns the child identity promptly; it does not keep the parent's Tool Call open until the child finishes. A user can open the child, observe its live stream, submit prompts and steer through the same single writer, without replacing its runtime. Subsequent user turns in the child do not generate further reports for the original task.

The application retains running parent and child runtimes independently of the current view; changing sessions, closing a view, and interrupting a parent do not abort its child. Idle runtimes with no pending work may unload and later restore from durable history. Direct interruption of a child may abort its run. Application shutdown aborts running children and records cancellation; an unclean shutdown leaves an unconfirmed task interrupted/unknown, never silently resumes model or tool work, and does not claim a confirmed cancellation. Print and JSON wait while spawned child tasks run, but if a child becomes idle without submitting its result, they exit with an explicit `awaiting_report` error and preserve the task and Session for later continuation; they do not auto-prompt the child. Without interactive approval support, their existing non-interactive Tool Permission policy remains fail-closed.

## Parent–child communication

A typed RPC-like contract inside the process connects parent and child. The parent Agent receives tools and instructions to list child metadata, inspect one task, send input to one child, cancel one active task, or cancel all active descendants; the LLM chooses these tools, and a user prompt never implicitly cancels children or preempts a busy parent. Task ID addresses status/cancellation; child Session ID opens the conversation. List results and individual status are bounded summaries, not a copy of every child transcript. `send_child` acknowledges only after input is committed to the child's durable inbox or Session, including when the runtime is unloaded. A busy child handles it through its ordinary input lane.

One task has at most one confirmed terminal outcome: success, failure, or cancellation. Cancellation does not delete a child Session, abort the parent's own turn, or replace an already committed outcome. The child Agent must explicitly call `submit_result` to report success; the parent inbox commits its structured, correlated report before the tool returns ACK. A child turn that ends without this call leaves the task `awaiting_report`, not successful. After ACK the delegated task's turn stops at a safe boundary, while the child Session remains available for later user prompts. A report never interrupts an in-flight model request or Tool Call. An active parent consumes its oldest report at the Stateful Agent's safe follow-up boundary, after committed steering, and processes it in the same turn. An idle Interactive/RPC Host automatically continues with the oldest inbox report, including after reopening; committed Steering Messages precede reports, which precede queued Submissions. Print/JSON do not auto-start idle report continuations. A task interrupted by an unclean shutdown has unknown outcome rather than an invented terminal report. Live progress may precede a checkpoint, but events that assert accepted steering, delivered/processed status, or committed content follow successful store commits. The existing `prompt()` admission and no-argument FIFO `steer()` behavior remain unchanged.

`submit_result` must be the only Tool Call in its model batch. A batch that combines it with any other Tool Call is refused before executing any tool in that batch, with no report or ACK; the child can issue a separate result call. This prevents a success report from racing concurrent tool side effects.

## Modes and session visibility

Interactive and external RPC can open an active child like a parent. Interactive/RPC Hosts automatically continue idle parent Sessions with pending reports; Print and JSON retain one-shot behavior and do not auto-prompt from an idle report inbox. RPC keeps Pi-style one active Session for default commands and realtime event delivery, but switching the active view does not tear down other running runtimes. This supersedes the one-Host-per-process and session-switch lifetime constraints in ADR-0025, not the established structured input, queue-head steering, attachment safety, or failure semantics. A background child Approval Request retains its Session identity and sends a minimal cross-session notice; details and settlement remain in the child Session. Print emits only parent assistant text while waiting for child tasks. JSON tags child events by Session ID and includes their terminal status without folding child text into the parent's answer. This revises the one-shot completion and RPC lifecycle clauses in ADR-0027.

The application retains one writer per Session ID, including while a runtime runs in the background. Multiple callers—including the parent Agent, the child UI, and an RPC client—send commands to that same authority; they never construct concurrent writable runtimes for the same Session. The writer-lock invariant in ADR-0034 remains, although its old one-Host-per-RPC-process note no longer applies.
